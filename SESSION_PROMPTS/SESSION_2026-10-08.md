## 2. How the design evolved (decisions in order)

1. **Frontend first.** Landing page shows floors 0 to 8 stacked vertically; clicking a floor reveals rooms 1 to 20. Login and logout. Students enter semester, course and batch. Teachers save name, courses taught, and where they work when free (classroom or office desk).
2. **Simple password login** (student password = the part of the SPIT email before `@`, passwords hashed, per-IP request limits). The weakness was raised: anyone who knows a student's email could work out the password.
3. **Final decision: no passwords at all.** Everyone logs in with an email one-time password (OTP) and receives a JWT. Students use their SPIT email. Staff accounts are created only by an admin.
4. **Stack decision:** Node.js with Express, PostgreSQL for data, Redis for OTPs, rate limits and token revocation. Backend in separate files. Admin interface included.

## 4. Authentication and security as implemented

**Login flow**
1. `POST /api/auth/request-otp` with an email. A 6-digit code is generated and stored in Redis as an HMAC (never plain), valid 5 minutes. It is emailed through SMTP; with `SMTP_HOST` empty it prints to the server console.
2. `POST /api/auth/verify-otp` with email and code. The code is single use and is deleted after 5 wrong tries. On success the server sets an httpOnly, SameSite=Strict cookie `cs_token` holding a signed HS256 JWT (user id, role, unique id). Default lifetime is 8 hours (`JWT_HOURS`).
3. `POST /api/auth/logout` adds the token's id to a Redis blocklist until it would have expired, so a copied token stops working.

**Who can log in**
- Any email ending in `STUDENT_DOMAIN` (default `@spit.ac.in`, **assumed, still to be confirmed**). A student account is created automatically on first login.
- Teachers, timetable managers, admins and the super admin only if an admin created them. An existing account always wins over the student rule, so staff on the same domain keep their role.
- The request-code reply is identical whether or not the email can log in, so addresses cannot be probed.

**Request limits (Redis counters)**
- Request code: 60 per 15 minutes per IP, 10 per hour per email, and one code per minute per email.
- Verify code: 100 per 15 minutes per IP.
- Whole API: 600 per minute per IP (`API_PER_MINUTE`).
- Set `TRUST_PROXY=1` when running behind a reverse proxy, otherwise every user looks like one IP.

**Other safeguards**
- The role is read from PostgreSQL on every request, not trusted from the token. Removing a user cuts access immediately.
- `helmet` security headers with a strict content policy. That is why the frontend uses separate `.js` and `.css` files and writes user-supplied text with `textContent`.
- JSON bodies capped at 10 KB, JSON-only API, SameSite cookie: together these cover CSRF.
- Parameterised SQL everywhere.

## 5. API summary

| Method and path | Who | Purpose |
| --- | --- | --- |
| POST `/api/auth/request-otp` | public, rate limited | Email a login code |
| POST `/api/auth/verify-otp` | public, rate limited | Check code, set JWT cookie |
| POST `/api/auth/logout` | logged in | Revoke token, clear cookie |
| GET `/api/me` | logged in | User and saved profile |
| PUT `/api/me/profile` | logged in | Student: semester, course, batch. Others: name, courses, free place (`classroom` or `office_desk`), free location |
| GET `/api/status` | logged in | All rooms occupied right now |
| PUT `/api/rooms/:floor/:room` | teacher, admin, superadmin | Set occupied (faculty, from, to) or free |
| GET `/api/admin/users` | admin, superadmin | List staff |
| POST `/api/admin/users` | admin, superadmin | Add staff. Admins create teachers and timetable managers; only the super admin creates admins. A student who already logged in is promoted |
| DELETE `/api/admin/users/:id` | admin, superadmin | Remove staff. Cannot remove yourself or a super admin; only the super admin removes admins |

## 6. Database (PostgreSQL)

`users` (role: student, teacher, timetable_manager, admin, superadmin), `rooms` (189 rows generated, type defaults to `classroom`), `student_profile`, `teacher_profile`, `live_status` (one row per occupied room; a free room has no row), `batches` and `timetable` (created, unique on room, day, time slot; **no code uses them yet**).

## 7. Conflict detection

The proposal's vector rule is implemented in `server.js`. A class is the vector (room, hour, floor). Two classes clash when the cross product is zero and the squared lengths are equal, which in practice means same room, hour and floor. Room updates run inside a transaction with a per-room advisory lock, so two requests for one room are handled one after the other. Allowed times are 08:00 to 17:00; a clash returns 409 "Room already occupied at this time."

## 8. Running it locally (macOS, no Docker)

```bash
brew install postgresql@16 redis
brew services start postgresql@16
brew services start redis
export PATH="/opt/homebrew/opt/postgresql@16/bin:$PATH"   # Intel Mac: /usr/local/opt/...
createuser classsync && createdb -O classsync classsync
psql -d postgres -c "ALTER USER classsync PASSWORD 'change-me'"

cd files/classsync
cp .env.example .env     # set JWT_SECRET (32+ random chars) and SUPERADMIN_EMAIL
npm install
PGPASSWORD=change-me psql -h localhost -U classsync -d classsync -f backend/schema.sql   # once only
npm run seed
npm start                # http://localhost:3000, codes print in this terminal
```

Docker was not installed on the development machine, so the Homebrew route was used.

## 9. Problems met and how they were handled

- **`npm install` and `cp` failed:** commands were run in the repo root instead of `files/classsync`. Fixed by changing into that folder.
- **Docker not available:** switched to Homebrew Postgres and Redis.
- **`git push` rejected (non-fast-forward):** GitHub has a commit the laptop lacks. Fix is `git fetch`, then `git reset origin/main` (keeps files), then recommit.
- **`node_modules` was committed** (hundreds of files). Fix: add `.gitignore` with `node_modules`, `.env`, `.DS_Store`, and recommit. If it ever gets pushed, `git rm -r --cached files/classsync/node_modules`.
- **A JWT secret was pasted into the chat.** Treat it as exposed and generate a new one before real use. Never commit `.env`.

## 10. Known limitations and risks

- Not tested end to end: no real Postgres, Redis or SMTP run was observed in this session. Package versions in `package.json` were not checked against the registry.
- `live_status` keeps one entry per room. A non-clashing update overwrites the earlier entry. The planned-timetable layer is needed to hold the rest of the day.
- Someone can repeatedly request codes for another person's email, which can use up that person's hourly allowance (cooldown plus 10 per hour). Acceptable for a pilot; revisit if abused.
- Rate limits are fixed-window counters; per-IP limits can hit many students sharing campus Wi-Fi. Tune the numbers once real traffic is known.
- If Redis is down, rate-limited routes and login fail with an error (fails closed).
- A removed staff member whose email is on the student domain can log in again as a student (read-only).
- No refresh tokens; users log in again after `JWT_HOURS`.
- Admins cannot see or manage student accounts.
- Student profile and teacher "free place" are stored but not displayed anywhere else yet.

## 13. Update: building managed by admin, timetable, red/green view

Requests: follow these notes and finish the site; red for occupied, green for free; admins add and name floors, classrooms and labs; admins add teachers; students log in with their spit.ac.in email; plain HTML, CSS and JS only (no frontend framework).

**Data model changes (`schema.sql` now runs on every start and is safe to rerun)**
- `floors (level, name)`: level orders the floors (0 = ground, top shown first); name is shown to everyone.
- `rooms (floor_id, name, room_type)`: type is `classroom` or `lab`; names unique per floor. Deleting a floor deletes its rooms; deleting a room deletes its bookings and timetable entries.
- `bookings` replaces `live_status`: teachers can book a room several times per day. Old databases are upgraded automatically: floors 0-8 become "Ground floor", "Floor 1" ..., rooms become "Room 1" ... "Room 20", and `live_status` rows move into `bookings`.
- `timetable` also unique on (batch, day, slot): a batch has one class per slot.

**Occupied now** = a booking for today covering the current time, or a timetable class for today's weekday in the current hour. All times are India time (Asia/Kolkata), computed in `schedule.js` regardless of the server's own time zone.

**New backend files**: `building.js` (building view, room schedule, bookings, admin floors/rooms), `timetable.js`, `schedule.js` (time helpers and the vector clash rule, used by both bookings and the timetable).

**New API**

### Time rules (follow-up)
- Time is strictly Asia/Kolkata (`schedule.js` uses `Intl` with that zone; no `TZ` setting needed). Pages show times as 12-hour with "IST".
- Booking From/To are dropdowns, 8:00 AM to 6:00 PM in 15-minute steps; the server rejects anything else (e.g. 07:45, 10:10, 18:15).
- Timetable now runs 8 AM to 6 PM (slots 8-17; schema check upgraded).
- The clash rule now uses 15-minute blocks instead of hours, so 09:00-09:30 and 09:30-09:45 can both be booked, while 09:15-09:45 clashes.
- Verified with the server deliberately running in America/New_York: it still reported India time.

### Hold and free (follow-up)
Request: a teacher should be able to hold or free a room; held = red, free = green.
- The room panel shows one big status box: red "Occupied till ..." with **Free this room**, or green "Free now" with the **Hold this room** form (From/To in 15-minute steps).
- Holds: any teacher can hold a free room; only the teacher who held it (or an admin) can free it.
- Timetabled classes: any teacher can **Free for today** (class cancelled or moved). Stored in the new `cancellations` table (timetable entry + date + who). The room turns green and can be held by someone else. Students see "Cancelled today" on that class. **Undo** is allowed for the teacher who freed it (or an admin), and is refused if someone has held the room since.
- New API: `POST /api/classes/:id/free`, `DELETE /api/classes/:id/free`. `GET /api/timetable` now returns `freed_today`.
- Verified on a copy of the local DB with two teachers: class makes room red → freed → green → held by the other teacher → red; permission errors (403) and the undo clash (409) behave as described; screenshots of both states checked.
